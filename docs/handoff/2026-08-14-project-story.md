# 2026-08-14 项目探索历程与协作背景

这份文档不是技术状态表，也不是脚本说明。它记录的是这个仓库为什么会出现、我们一路上怎样改变判断、哪些方向曾经看起来合理但后来被推翻，以及为什么现在会形成这些维护规则。

下一位接手的模型应该把它和 `docs/handoff/2026-08-14-next-conversation.md` 一起读。后者回答“现在有什么、下一步做什么”，本文回答“为什么会走到这里、哪些事情不要重新忘掉”。

---

## 一、这个仓库一开始不是为了“修一个 Jellyfin bug”

项目最初面对的是一个很生活化的问题：用户已经有一套自己长期使用的动画收藏方式，但 Jellyfin 对动画文件名和目录的理解并不总能适应这套收藏。

用户的动画不是为了 Jellyfin 临时整理出来的素材，而是自己的长期收藏。目录里保留年份、季度、作品目录，视频文件本身保留字幕组发布时的原始文件名。这里面包含字幕组名、版本、分辨率、编码、集数标记等信息。

因此从一开始就有一个很重要的价值取向：

> **目标是让 Jellyfin 更好地理解现有收藏，而不是为了迎合 Jellyfin，把整个收藏重命名成它喜欢的样子。**

这也是为什么用户一直不愿采用“把所有文件改成 `S01E01.mkv` 就完了”这种看起来最省事的方案。不是不知道这种方法，而是它会把播放器的要求反过来施加到原始收藏上。

项目最初的理想状态其实很克制：

- 原始年份 / 季度目录不动；
- 字幕组原始文件名不动；
- 正常识别的动画不要干预；
- 只有明确识别错误的条目才补一点额外信息；
- Jellyfin 继续负责海报、简介、演员等它本来擅长的事情；
- 我们只修它从文件名 / 路径里读错的部分。

所以最早自然想到的是 **NFO**。它看起来正好符合“给 Jellyfin 多一点提示，但不改原始媒体”的思路。

## 二、为什么从一次性修补变成了 GitHub 仓库

最初完全可以把它当一次性脚本：扫一遍当前动画，写几个 NFO，结束。

但很快就发现动画库不是静态的。季度会继续增加，新番会继续下载，字幕组命名方式也不统一。今天手动修完，下一季度还会再来一次。

因此用户很早就决定，不要把这件事做成桌面上散落的一堆临时脚本，而是建立一个可以长期维护的 GitHub 仓库：

```text
leo-grayrat/jellyfin-anime-maintenance
```

这一步的意义不只是“代码放 GitHub”。它逐渐形成了几个长期目标：

1. 把规则、脚本、报告和历史结论放在一起，而不是只保留最终脚本；
2. 每次新季度可以复用，不用重新从聊天记录里找命令；
3. 让失败实验也有记录，因为失败往往决定下一步方向；
4. 通用脚本可以公开，但原始完整文件清单、Jellyfin 导出、API Key 等私人数据不上传；
5. 如果以后别人也遇到类似字幕组命名 / Jellyfin 识别问题，这个仓库至少能提供可复用的调查和工具。

这也是后来为什么用户不断要求“把东西放进仓库，不要只留在沙箱 / 对话里”。仓库本身就是这个项目的长期记忆。

## 三、第一阶段：我们以为 NFO 会是一个很干净的答案

最早的错误看起来很像普通的 season / episode 解析问题。

例如：

- 明明是第二季、第三季，被 Jellyfin 放进第一季；
- 季度目录中的 `2026-01`、`2026-07` 等数字似乎干扰了识别；
- 某些字幕组文件明明写着 `[09]`，Jellyfin 却显示成别的集数；
- 有的作品甚至出现第 2025 季、第 2026 季之类显然不合理的结果。

当时的直觉很简单：既然 Jellyfin 从文件名猜错，那我们就在旁边写一个最小 NFO，明确告诉它 season / episode。

这个方向一开始非常符合用户的目标：不改原视频、不重命名、只修异常项。

我们于是建立了 correction rule，最终生成了 243 个 production target NFO。

但第一个重要转折很快出现了：**写完 NFO 后，并没有出现“整个问题都被修好”的效果。**

这就是 issue #4 的起点。用户当时很直接地指出：只有部分“全都被识别成同一集”的动画看起来分出了不同集数，其他问题基本没动。

这件事很重要，因为它第一次打破了“问题只是 S/E 数字不对”的假设。

## 四、PowerShell 5.1 事故让仓库第一次真正有了工程维护意识

在很早的阶段，脚本还撞上了 Windows PowerShell 5.1 对 UTF-8 无 BOM 中文源码的解析问题。

这件事本身和 Jellyfin 根因无关，但它改变了项目的维护方式。

用户要求不要只在聊天里说“改好了”，而是把问题放进 issue、修复走 PR、加回归检查。这于是形成了早期 issue #1 和 PR #3。

从这里开始，项目逐渐意识到：

> “逻辑上应该能跑”不等于“用户机器上真的能跑”。

后面几乎所有重要工具都因此越来越强调 Windows PowerShell 5.1 实测、dry-run、preflight、日志和回滚边界。

这条经验后来反复救了项目。

## 五、Jellyfin 12 给了希望，但也暴露了更深的问题

后来我们确认 Jellyfin 12 已经包含上游关于 episode NFO season merge 的修复，于是重新测试 NFO 路线。

单集实验成功了：FullRefresh 后，Episode 自身的 `ParentIndexNumber` 确实能从错误季号变成 NFO 指定的季号。

当时这是一个很令人振奋的结果，因为它证明 NFO 不是完全没用。

但下一秒又出现了新的矛盾：

```text
ParentIndexNumber 已经是 3
SeasonId / SeasonName 却还挂在第 1 季
```

于是又做 Series refresh，层级才重新挂正确。

这段经历告诉我们：即使一个数字字段已经正确，也不能马上说“这个 Episode 修好了”。Jellyfin 内部还有层级关系、可见性、多版本关系等别的状态。

之后批量刷新时，又发现一批目标根本在正常 `/Items` 查询里找不到。

这才把调查真正带到 **hidden Episode** 上。

## 六、最大的转折：原来很多“消失的集数”不是没导入，而是被藏成了 LocalAlternateVersion

继续扩大查询之后，我们发现那些“找不到”的文件其实还在 Jellyfin 里，只是变成了别的 Episode 的本地多版本 child。

这个发现彻底改变了问题定义。

以前以为：

```text
文件 -> Jellyfin 识别错 season / episode
```

后来才知道部分情况其实是：

```text
多个不同物理 Episode
    -> Jellyfin 很早就认为它们是“同一集的不同版本”
    -> 只显示一个 owner
    -> 其他文件变成 hidden LocalAlternateVersion
    -> 后来 NFO 即使把 child 的 S/E 改正确，也不会自动解除这层关系
```

这解释了为什么“数字已经修正了，UI 还是怪的”。

也说明 NFO 路线只能解决问题的一部分。

## 七、我们一度怀疑数据库残留，但实验把这个解释推翻了

发现 LocalAlternateVersion 后，一个自然猜测是：

> 会不会只是旧数据库里已经留下了错误关系？只要删除 / 重建，或者直接改关系，就能恢复？

因此做了 SQLite 只读诊断，也做了单集 remove / re-add 实验。

结果非常关键：**同一个原始文件名重新加入后，错误 LocalAlternateVersion 分组会再次被 Jellyfin 主动建立。**

这说明问题不是单纯的历史脏数据。

如果我们当时直接写 SQLite 把关系拆掉，看起来可能暂时正常，但 Jellyfin 下次扫描仍可能重新制造同样的问题。

因此项目形成了一个重要原则：

> 不直接把“改数据库”当正式修复方案。先找到 Jellyfin 为什么会再次做出这个判断。

这也是后来一直坚持“DB 可以只读诊断，但不要直接写关系”的原因。

## 八、真正抓到路径解析：`YYYY-MM` 竟然会参与 Episode 识别

为了隔离变量，我们做了更小的实验。

把同一个 Medalist Episode 用显式 canonical 名称重新放入：

```text
S02E09 - 原文件名.mkv
```

它就能独立导入。

跨作品的实验也得到相同结果。

继续对照 Jellyfin 路径解析逻辑后，才逐渐确认：Jellyfin 在 TV Episode 解析阶段会看**完整路径**，而不仅是最后的文件名。祖先目录中的：

```text
2026-01
2026-04
2026-07
```

可能被宽泛的“数字-数字”模式提前吃掉。

于是一个非常反直觉的事实出现了：

> 用户为了管理动画而使用的季度目录，本身可能参与 Jellyfin 的 Episode key 解析。

这件事是整个项目最重要的根因之一。

而它也让最初的价值取向再次变得重要：最简单的办法当然是“把原目录重命名 / 搬走”。但用户从一开始就不想为了 Jellyfin 改造原始收藏结构。

所以我们需要一种“原始收藏不动，但给 Jellyfin 另一种安全视图”的方案。

## 九、canonical view 不是炫技，而是原始目标被逼出来的折中

canonical view 的想法因此出现：

```text
原始动画收藏完全不动
        ↓
同盘 hardlink
        ↓
给 Jellyfin 一套显式 SxxEyy 的规范文件名
```

这不是因为我们特别想引入 hardlink，而是它同时满足几个互相冲突的要求：

- 用户不愿重命名原视频；
- 不想复制几百 GB / TB 的视频；
- Jellyfin 又确实需要一个更明确的输入名字；
- 方案必须可撤销、可重建，而不是对原收藏做不可逆修改。

因此 canonical view 是“让 Jellyfin 适配收藏”这个最初目标的工程化结果。

中间又遇到了 Windows 路径里的 `[02]` 被 PowerShell provider 当通配符、MAX_PATH、`GetPathRoot` 等问题，最后逐渐把关键文件操作换成 Win32 native API。

第一阶段 243-target canonical view 最终成功 Apply，第二次 dry-run 也证明它幂等、可复用。

这是一个真正的阶段性成功。

但它还不是整个项目的结束。

## 十、一个很重要的协作转折：我们差点又把“旧问题”忘了

243-target canonical view 成功后，技术上很自然的下一步是继续做 Phase 2：把完整 TV 库都映射进 View，然后切换 Jellyfin。

这时用户主动叫停。

原因不是 canonical view 有新 bug，而是用户重新翻 Jellyfin UI 时发现：**标题、简介、海报、作品识别等老问题仍然存在。**

例如：

- Fate/strange Fake 的 Episode title 变成 `[晚街与灯`；
- Medalist 显示 `Medalist`、`Medalist[S2`；
- 100 女友第三期虽然 S03E01 已经正确，但 Episode 名还是 `Hyakkano`，Series 海报也不完整；
- 名侦探光之美少女很多集标题都变成 `[FLsnow`。

这次用户提出了一个对整个项目都非常重要的批评：

> **不要每发现一个新问题，就把之前的问题忘掉；也不要每解决一个技术点，就默认项目整体已经往前走了一层。**

这不是一句普通的提醒。

此前我们确实多次发生这种模式：

```text
发现 A
 -> 深挖 A
 -> 找到 A 的漂亮解释
 -> 开始围绕 A 设计下一套工程
 -> B、C、最初目标逐渐退出上下文
```

canonical view 成功后差点直接进入全库切换，就是这种模式的典型例子。

因此我们暂停 Phase 2，决定重新把“结构问题”和“metadata 问题”放回同一张图里。

## 十一、为什么后来一定要做统一 audit / ledger

统一 audit 的目的从来不只是“导出一个更大的 JSON”。

它是为了对抗我们自己的上下文遗忘。

我们需要一个东西，让每次下一步决策都能同时看到：

- S/E 是否正确；
- Episode 是否 hidden；
- Season 是否异常；
- 是否属于 243 correction targets；
- Provider ID 是否缺失；
- Overview / image 是否缺失；
- title 是否跨集重复；
- 文件系统里有没有 Jellyfin 完全漏掉的文件；
- SP / OVA / NCOP / NCED / PV / menu / Bonus / 特典等有没有被误当普通 Episode。

因此 audit 和 analyzer 的真正意义是建立一个**项目记忆外置化**的机制。

以后不能再只靠当前聊天上下文说“我们记得还有这个问题”。

## 十二、统一 audit 的开发过程本身，又验证了“真实运行比看代码重要”

这个阶段连续遇到了很多看起来很小、但都只有真实 Windows 环境才会暴露的问题：

- NFO 明明存在，但 245/245 全部 `ReadAllText` 报路径非法；
- 改成 `CreateFileW` 后，同一个 PowerShell 进程仍然在跑旧的 Add-Type 类型；
- analyzer 一个 Markdown 反引号转义让下一行 `Generated:` 才报 parser error；
- 参数名 `$Input` 撞上 PowerShell 自动变量 `$input`；
- Mandatory `List[string]` 不接受空集合；
- analyzer 已经能跑全库以后，我们又发现 Season 层根本没进账本。

这些事故并不是这份 story 最重要的技术知识，但它们塑造了工作方式：

> **不能因为代码审查看起来合理，就宣称完成。用户机器上的真实 PASS 才算完成。**

特别是最后那个 Season 漏项非常具有代表性：工具已经“成功”了，但如果不是重新检查最初目标，我们又会把旧的 `未知季 / 第 2026 季 / SPs / Bonus / 特典映像` 问题从账本里遗忘。

于是 Season 被补回统一 ledger。

最终用户真实运行得到：

```text
Series rows:                 56
Season rows:                 92
Expanded Episode rows:       676
Correction-target NFO rows:  243
Hidden Episode rows:         190
Hidden correction targets:   157
Hidden non-target rows:      33
Filesystem-only rows:        0
```

这才算 audit 阶段真正完成。

## 十三、另一个差点走错的解释：`EnableInternetProviders=false`

在排查 metadata 时，我们一度看到 JSON 里的：

```text
EnableInternetProviders = false
```

很容易据此得出“Jellyfin 网络 metadata 被关掉了”的结论。

但进一步对 Jellyfin 12 源码和 TypeOptions 对照后发现，这个字段已经 obsolete；真正的 remote provider 配置仍然存在。

因此这个漂亮、简单、能解释一切的说法被推翻。

这件事再次提醒下一位模型：

> 当一个解释能一下子解释很多现象时，尤其要确认它是真的，而不是因为它很方便。

## 十四、metadata 问题又让我们学会：不同坏相不一定是同一个根因

统一 audit 之后，几个代表病例明显不是同一种故障：

- Medalist：Provider ID、Overview、图片都有，但 Name 仍错；
- Fate/strange Fake：Name 错，同时 Provider ID / Overview 也缺；
- 100 女友第三期：Series 已部分识别，但 Episode metadata 明显不完整；
- 光之美少女：Episode 已正常 visible，但 title 仍然错误。

因此不能再用一句“刮削失败”概括它们。

源码调查目前给 Medalist 提供了一个很强的解释：早期为了安全修 S/E 使用的 `FullRefresh + replaceAllMetadata=false` 会运行 provider，却不会替换已经非空的旧 Name。

这很可能解释“其他 metadata 已经拿到，错误标题却一直留着”。

但我们没有因此马上全库 ReplaceAll。

现在停在一个受控的 Medalist S02E01 单集实验，就是因为我们一路上已经学会：

> **先用一个变量明确的病例证实，再扩大；不要因为源码解释漂亮，就直接把它当全库方案。**

## 十五、为什么剧场版后来被主动冻结

项目中间也出现过电影 / 剧场版的异常。

但用户明确要求当前先只处理 TV。

这不是“忘了剧场版”，而是有意控制范围：`D:\Gekijouban` 中混有剧场版、OVA、SP、特典和其他额外内容，分类本身比 TV 更复杂。

如果在 TV 主线还没稳定时把它一起拉进来，只会让问题定义继续膨胀。

所以“剧场版以后单独处理”是一个主动的项目管理决定，而不是遗漏。

## 十六、issue 被遗忘，是一次协作层面的倒退

仓库早期其实已经建立了 issue / PR 工作流。

但随着后面实验越来越多，我在对话里逐渐沉入技术调查，issue 反而很久没有持续更新。

用户在 2026-08-14 专门指出了这件事：

> 很久以前就说过要用 issue 记录问题，但后来完全被忘掉了。

这是很典型的“工具还在，工作方式却丢了”。

因此现在重新明确：

```text
问题出现
 -> 先查 / 建 issue
 -> 调查证据持续回填
 -> 修复走对应分支 / PR
 -> 用户真实环境验证
 -> merge
 -> 关闭 issue
```

issue 不是为了形式完整，而是为了让下一次对话、下一个模型知道：哪些问题真的解决了，哪些只是暂时绕过，哪些还在 open。

目前：

- #4 是结构主线；
- #5 是 metadata 主线；
- #8 是 Add-Type 缓存这个已知但未永久修复的问题；
- #6 对应统一 audit，已经通过 PR #7 合入并关闭。

## 十七、文档语言也暴露了“模型容易进入自己的默认模式”

`docs/history/2026-08-14-episode-metadata-refresh-root-cause.md` 最初被我直接写成了英文。

技术上没有任何理由。

这个仓库的说明、history、issue 一直主要是中文，用户也明确希望整个维护过程以中文记录。英文版只是模型在写源码调查时滑回了自己的默认技术写作习惯。

用户指出后已经改回中文。

这件事看似很小，但它和前面的工作方式问题是同一种东西：

> 不要因为模型自己觉得某种形式“专业 / 顺手”，就忘记这个项目已经形成的实际习惯和用户目标。

## 十八、一路上真正形成的原则

如果只看最后的技术方案，很容易觉得这个项目就是：NFO + hardlink + audit + metadata refresh。

其实更重要的是一路上形成的判断原则。

### 1. 原始收藏优先

原始视频、字幕组文件名、年份 / 季度目录是用户的收藏，不是 Jellyfin 的临时输入缓存。

正式方案尽量围绕它建立适配层，而不是修改它本身。

### 2. 最小干预优先

正常条目不为了“统一”而重写。只对已经确认异常的目标做修复。

这也是为什么 33 个 non-target hidden 不能因为“看起来也藏着”就自动处理。

### 3. 可逆比省一步重要

NFO、hardlink View、dry-run、manifest、只读 audit，这些设计都在尽量让操作可追踪、可撤销、可重建。

### 4. 不直接拿数据库当修复入口

数据库适合诊断，但如果 Jellyfin 的解析逻辑会重新制造错误关系，直接改 DB 只是把症状擦掉。

### 5. 不把局部成功写成全局结论

单集实验成功，只证明那个变量；canonical prefix 成功，不代表 metadata 已解决；Medalist 如果 ReplaceAll 成功，也不代表 Fate / 100 女友同根因。

### 6. 不要只追最新的问题

结构、metadata、Season、extras、文件覆盖都必须能回到统一账本复核。

### 7. 真实环境验证是完成条件

尤其是 Windows PowerShell 5.1、长路径、Jellyfin 12 API 这种环境相关行为，用户机器的实际运行结果优先于静态推断。

### 8. 仓库是项目记忆，不是代码垃圾桶

history 要记录“当时为什么这么判断”；issue 要记录“这个问题现在到底 open 还是 closed”；PR 要对应已经验证的阶段；失败实验应该保留，但不要伪装成正式工具。

## 十九、给下一位模型的一段话

接手这个项目时，不要把自己理解成“来继续写几个 Jellyfin 脚本的人”。

真正的任务是：

> 在尽量不破坏用户原始动画收藏方式的前提下，让 Jellyfin 能长期、稳定、可维护地正确理解这套收藏。

仓库已经经历过几次“一个漂亮技术解释吸走全部注意力”的阶段。每次新的发现都值得追，但追之前要问：

- 它解决的是最初哪个用户体验问题？
- 它和 #4 / #5 另外一条主线是什么关系？
- 有没有旧问题因为当前调查而退出视野？
- 这是源码推断、单集实验，还是已经全库验证？
- 如果失败，原始媒体是否仍然安全？
- 这个结论是否应该进入 issue / history，而不是只留在聊天里？

如果能一直保留这些问题，下一阶段即使继续遇到新的 Jellyfin 奇怪行为，也不会重新走回我们已经绕过的那些弯路。
